# Authorization policy design

Status: **design only**. Nothing in this document is implemented yet. It exists
because roadmap §4 requires the policy design to be settled before any
per-session authorization code lands.

Related: [`SECURITY.md`](../SECURITY.md) (threat model), `architecture.md` §7
(endpoint boundary), `known-limitations.md` §12 (same-user access).

## 1. What the policy is for

The endpoint already restricts *other unprivileged users*: `0700`/`0600` on
Unix, an owner/`SYSTEM`/Administrators DACL on Windows. Any process running as
the same user can still drive every agent - that is the accepted boundary
(`SECURITY.md` T1).

A policy adds **cooperative least privilege inside that boundary**. Typical
uses:

* an MCP server that should only read two named agents, never spawn or kill;
* a build script that may send into `builder` but must not attach anywhere;
* a reviewer tool that should not be able to `shutdown`.

It is a guardrail against a misconfigured or over-broad tool, and against
mistakes such as a typo that names the wrong agent. It is **not** a defence
against hostile code running as the same user: such code can read the policy
file or the bearer token, exactly as it can read `~/.ssh`. That is stated
plainly so nobody mistakes the policy for a sandbox.

Non-goals for the first implementation:

* isolating two same-user principals from each other (impossible without a new
  OS boundary such as a service account, a sandbox or a separate daemon);
* remote or multi-user access (roadmap §10);
* per-agent *process* confinement (agents run with the user's full privileges);
* content validation or redaction (a separate roadmap item);
* an audit trail (separate roadmap item).

## 2. Identity: bearer tokens, not OS users or `from`

The OS can tell the daemon only "same user" or "not the user". Peer credentials
on Unix and the client SID on Windows therefore cannot separate two same-user
tools.

`from` is a caller-supplied label and stays that way (`protocol.rs:290-291`).
It is recorded in the message log and shown in listings, and it never
authenticates anything.

The policy introduces a **bearer token** per policy rule:

* the daemon stores the token material in the policy file, reads it once at
  startup and compares it in constant time;
* clients present it as `AGENT_BRIDGE_TOKEN` in the environment or `--token` on
  the command line (CLI change lands with enforcement);
* the token is a random 32-byte value, printed once when created, prefixed
  `abt_` so it is recognisable in logs and secret scanners;
* a request without a token, or with an unknown token, is **unauthenticated**
  and falls under `default` (deny, if the file exists);
* tokens are per rule, not per agent. One token may cover a set of agent names.

The token must never be inherited by spawned agents through the daemon's
environment: the daemon gets policy tokens from the file, and agents inherit the
daemon's environment (`agent.rs:143-158`). A tool that launches an agent and
also needs the bridge passes `AGENT_BRIDGE_TOKEN` explicitly to that child, or
uses `--token`. Enforcement must therefore **scrub `AGENT_BRIDGE_TOKEN` in
`Agent::spawn` before the general environment allowlist lands**, otherwise
`AGENT_BRIDGE_TOKEN=x agent-bridge daemon start` would hand the token to every
agent it later spawns. Environment sanitisation is a separate roadmap item and
must preserve this rule.

## 3. Location and format

* Default path: `<state>/policy.json`, next to `daemon.sock` and `daemon.log`
  (`paths.rs:20-36`).
* Override: `AGENT_BRIDGE_POLICY=/absolute/path/policy.json`. Relative paths are
  rejected, so a policy cannot be picked up accidentally from the current
  directory.
* Format: **JSON**, parsed with the existing `serde_json` dependency. TOML
  would read slightly better for humans, but it would add a parser dependency
  to the daemon for no behavioural gain; the file is generated by a command
  and reviewed rarely. Comments are not available, so every field is
  self-describing and documented here.
* Permissions: the file must be owner-only. On Unix the daemon refuses to load
  a policy whose mode has any group/other bit set (`0o077`), and refuses to
  load one it does not own. On Windows it refuses if the file's DACL grants
  anyone beyond the owner, `SYSTEM` and Administrators. Refusing is deliberate:
  a policy that any same-user process can rewrite is worse than no policy,
  because it looks enforced.
* Size: the file is capped at 256 KiB, so a malformed or hostile file cannot
  grow daemon memory (same reasoning as the request-frame gap in
  `SECURITY.md`).

## 4. Schema, version 1

```json
{
  "version": 1,
  "default": "deny",
  "rules": [
    {
      "name": "mcp-readonly",
      "token": "abt_2f8c...",
      "allow": ["list", "read"],
      "agents": ["builder", "reviewer"],
      "read_bytes": 65536
    },
    {
      "name": "ci",
      "token": "abt_77a1...",
      "allow": ["create", "write", "terminate"],
      "agents": ["ci-*"],
      "max_message_bytes": 8192
    }
  ]
}
```

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `version` | integer | required | Schema version. Unknown values refuse to load. |
| `default` | `"allow"` / `"deny"` | required | Verdict for an unauthenticated client, or a request no rule covers. |
| `rules[].name` | string | required | Unique label shown in errors and logs. `^[a-z0-9][a-z0-9_-]{0,63}$`. |
| `rules[].token` | string | required | `abt_` followed by 64 lowercase hex characters. Unique. |
| `rules[].allow` | array of verbs | `[]` | Verbs this rule grants. Empty means "nothing", not "everything". |
| `rules[].agents` | array of names | `["*"]` | Agent-name patterns the rule applies to. `*` matches every name; a trailing `*` is a prefix match; anything else is exact. No `?`, no character classes. |
| `rules[].read_bytes` | integer | `65536` | Per-response cursor-read cap for this rule, clamped to `MAX_READ_CHUNK` (`daemon.rs:41`). |
| `rules[].max_message_bytes` | integer | global limit | Per-message cap for this rule, clamped to the daemon-wide limit (`delivery.rs:19`, `delivery.rs:78-87`). |

Unknown fields are a **load error**, not ignored: a typo such as `"alow"` must
not silently produce a rule that grants nothing while looking correct. This is
the opposite of the wire protocol's unknown-field tolerance, and deliberately
so.

## 5. Verbs and request mapping

A verb is what a rule grants. Every request maps to exactly one verb, so
enforcement has no gap:

| Verb | Requests | Scope |
| --- | --- | --- |
| `list` | `List`, `Ping`, `Version` | global |
| `read` | `Read` (line and cursor views) | one agent |
| `attach` | `Attach` stream, including the `Input`/`Resize` it carries | one agent |
| `write` | `Send`, `Ack`, `Input`, `Resize` outside attach | one agent |
| `create` | `New` | the new agent's name |
| `terminate` | `Kill` | one agent |
| `log` | `Log`, `MessageStatus`, `Pending` | global |
| `shutdown` | `Shutdown` | global |

Notes:

* `Ping` and `Version` are granted to everyone, token or not, because the CLI
  needs them to discover a protocol mismatch before it can present a token.
  They reveal only the protocol number and daemon version.
* `attach` is authorized once, when the stream starts. A policy reload or
  rotation does not cut an open stream; document that when reload lands.
  `Input`/`Resize` sent over an authorized attach stream are covered by
  `attach`, not `write`, otherwise attaching would be useless.
* A keystroke path outside attach (`Input`/`Resize` as standalone requests) needs
  `write` for that agent.
* `Ack` is a write: it changes delivery state. It is target-checked against the
  message's agent, then authorized for that agent.
* `shutdown` is deliberately global and never implied by another verb.

## 6. Matching and precedence

The algorithm is small enough to state exhaustively:

1. Find the rule whose token equals the presented token (constant-time; an
   empty or unknown token matches nothing).
2. If no rule matched, the verdict is `default`.
3. If the request is global (`list`, `log`, `shutdown`), it needs that verb in
   the rule's `allow` list.
4. If the request names an agent, the rule must both allow the verb **and**
   match that agent against `agents`.
5. **Deny wins.** An explicit `"deny"` list is checked first and overrides any
   allow at the same or broader level. v1 has no `deny` list; the field is
   reserved so a later version can express "this tool may do everything except
   terminate" without rewriting every allow.
6. No other source of authority exists: the policy file is the only input.
   There is no union with the CLI's own flags, and no per-request override.

When (5) lands, precedence is: rule deny for agent > rule allow for agent >
rule allow for `*` > `default`. Deny at any applicable level stops the request.

Determinism matters more than expressiveness here: two matching rules are a load
error (duplicate token or duplicate name), so there is never a "which rule won"
question.

## 7. Secure defaults and failure modes

| Situation | Behaviour |
| --- | --- |
| No policy file | Legacy behaviour: every same-user client may do everything. Logged once at `info` with the path that was checked. |
| Policy file present, client sends no token | `forbidden` for everything except `Ping`/`Version`; `default` decides, normally `deny`. |
| Policy file present, `default: "allow"` | Unknown clients may do every verb for every agent (v1 has no deny lists). Discouraged; logged at `warn` on startup. |
| File unreadable, malformed, unknown field, unknown version, duplicate name/token, bad pattern | **Daemon refuses to start.** The error names the path and the first schema problem. Never fall back to allow-all. |
| File mode too permissive (Unix) | Refuse to load, naming the required mode. |
| Rule allows a verb no request maps to | Load error (unknown verb), so typos fail loudly. |
| Agent named in a rule never exists | Not an error. Rules are declarative; agents come and go. |
| Token missing from the policy but presented by a client | Treated as unauthenticated; `default` applies, and the daemon logs a rate-limited warning without echoing the token. |

A policy file makes the daemon fail closed. That is the whole point: a broken
policy must stop the daemon, not silently reopen the endpoint.

## 8. Enforcement points and error surface

* All enforcement goes through one function called at the top of
  `try_handle` (`daemon.rs:212-528`), after the request is parsed and before
  any side effect. No handler checks permissions itself.
* Authorization runs before `get(target)`, so an unauthorized client cannot use
  `not_found` versus `forbidden` to enumerate agent names it may not see.
  `read` against a forbidden agent therefore answers `forbidden` whether or not
  the agent exists.
* Denials are a new wire error, `forbidden`. `ErrorCode` is a closed enum
  (`protocol.rs:43-60`), so adding it requires a **protocol bump** to v10: an
  old client would fail to parse the new code. The version handshake already
  restarts a daemon only when it owns no agents (`main.rs:630-670`).
* A denial returns no agent data: no name confirmation beyond what the caller
  supplied, no output, no status.
* Attach streams check authorization before the first replayed byte.
* `shutdown` and `kill` denials are logged at `info` with the rule name (never
  the token, never the message body).

## 9. Token handling

* Generation: `agent-bridge policy token new <rule-name>` (lands with
  enforcement) writes a new rule with a fresh token and prints the token once,
  to stdout only. A convenience path, not required; hand-editing is supported.
* Storage: plaintext in the owner-only policy file. A hash would be better
  against casual file reads, but a hash crate is a new dependency and same-user
  code can read the plaintext just as easily from the file or the client's
  environment. Revisit when a maintained hash crate is already in the graph.
* Comparison: constant time in the daemon, so a local client cannot learn a
  token prefix by timing.
* Rotation: edit or replace the file, then restart the daemon. Live agents keep
  running across a *policy* restart only if the restart path is added; v1
  deliberately does not reload on SIGHUP, because a half-written file must not
  become the active policy. `daemon reload` is a follow-up.
* Leakage: tokens are secrets. The CLI never logs them; `--token` on the command
  line is visible in process listings, so `AGENT_BRIDGE_TOKEN` is preferred.
  Debug output redacts `abt_...` strings.
* Rotation after suspected leak is the only remedy; there is no per-token audit
  trail yet.

## 10. Compatibility and migration

* Absent policy file: unchanged behaviour, so an upgrade cannot lock anyone out.
* Adding the policy is opt-in and local to one daemon instance (state dir or
  `AGENT_BRIDGE_POLICY`).
* Protocol v10 ships with the first enforcement PR; the CLI and daemon are
  released together, and a mixed pair triggers the existing skew handling.
* The MCP adapter (roadmap §5) must carry a token and advertise only the tools
  its rule allows.
* Documentation to update with enforcement: `README` (how to enable),
  `architecture.md` §7 (policy as the second boundary), `SECURITY.md` (policy
  is not a malware defence), `known-limitations.md` §12 (what remains open),
  and this file (status changes from design to implemented).

## 11. Testing plan

Unit tests (no daemon):

* token comparison rejects empty, unknown, wrong-length and prefix tokens;
* pattern matching: exact, suffix `*`, `*` alone, names with digits/dashes;
* precedence: deny beats allow, agent-specific beats `*`, unmatched falls to
  `default`;
* load errors: unknown field, unknown verb, duplicate name, duplicate token,
  bad mode, oversized file, unsupported version;
* constant-time compare is used (code review, not timing measurement).

End-to-end tests (one daemon per test, isolated state):

* read-only token: `Read` succeeds on its agents, `Send`/`Kill` answer
  `forbidden`; a different agent answers `forbidden`, not `not_found`;
* write token: `Send` works, `create`/`terminate` denied;
* absent token with `default: deny`: only `Ping`/`Version` work;
* absent policy file: legacy allow-all still passes the existing suite;
* malformed policy: daemon exits non-zero with the schema error, no endpoint
  left behind;
* Unix mode check: `0644` policy refuses to load;
* protocol skew: v9 client against v10 daemon restarts only when no agents are
  live.

Acceptance for the enforcement PR is the roadmap §4 criterion: a negative test
for each protected operation (read, write, create, attach, terminate), plus
`shutdown`.

## 12. Open questions

Deferred until enforcement, not blockers for this design:

* whether `deny` lists are needed in v1 or only in v2 (reserved now);
* reload without a restart, and whether an open attach stream survives it;
* hashing tokens at rest once a hash crate is justified;
* whether rules should be scoped by message *direction* (send versus ack);
* interaction with the future audit log (rule name and verdict per request);
* whether `create` should also constrain argv or cwd (today `cwd` is trusted
  input; path validation is a separate roadmap item).
